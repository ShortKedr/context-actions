**Context Actions — цель и план развития**

Рабочая продуктовая заметка от 7 сентября 2026 года. Описывает дальнейшую разработку; перечисленные возможности и показатели ещё не реализованы и не измерены.

**Цель.** Создать Context Actions — лёгкое, быстрое и полностью самостоятельное дополнение к Windows 11 для повседневной работы с файлами. Пользователь выбирает файл или несколько файлов в Проводнике, вызывает понятное действие и получает результат за минимальное число шагов. Приложение предназначено сразу для автора и других пользователей и должно ощущаться естественной частью Windows, «будто бы так и было задумано».

Главный результат направления — улучшение UX работы с файлами. Скрипты и конвертеры служат этой цели. Ближайший референс — Quick Actions и соседние файловые действия macOS Finder; ориентир по отзывчивости — 7-Zip.

**Зафиксированные требования.**

- Пункт **Context Actions** с понятной, читаемой иконкой присутствует в современном и классическом контекстных меню Windows 11.
- Внутри — короткий набор действий по типу выбранных файлов. Последний пункт всегда **More Actions…**, открывающий приложение с уже переданным выделением.
- Минималистичный интерфейс, быстрый запуск, понятные настройки, прогресс, отмена и доступ к результату.
- Локализация меню, приложения и сообщений: английский, русский, немецкий, французский, китайский. Для китайского рабочее допущение — упрощённый, `zh-CN` / `zh-Hans`; пользователь указал `cn`.
- Полный **Self Packaged** для обязательных функций: FFmpeg, кодеки и все остальные необходимые движки, библиотеки и дополнительные runtime входят в поставку и находятся внутри каталога приложения. Для этого набора пользователю не требуется устанавливать Office, LibreOffice, Python, FFmpeg, настраивать PATH или скачивать компоненты при первом запуске.
- Согласованное исключение: если PDF с полным исходным оформлением нельзя получить автономно, такая операция предоставляется дополнительно через установленный Excel/Word. Она остаётся в интерфейсе и без Office; доступность проверяется при первой попытке, результат сохраняется на локальном диске, отсутствие нужного приложения объясняется пользователю, действие помечается недоступным.
- Только бесплатные компоненты. Python-скрипты и Python runtime в продукте запрещены. Базовый стек должен обходиться без тяжёлых платформ и сложной цепочки зависимостей; платные SDK не рассматриваются.
- Идеальный размер **полного сжатого установщика — до 100 МБ**, допустимый предел установщика — **300 МБ**. Он включает приложение, все комплектные движки, DLL, ресурсы, локализации, необходимые шрифты и runtime для целевой архитектуры. **300 МБ после установки при установщике 100 МБ — хороший результат и соответствует целевому бюджету.** Установленный размер измерять отдельно; лимит 300 МБ на него не распространяется.
- **Если готовый полный установщик превышает 300 МБ, представить состав и измерения и задать пользователю вопрос о новом лимите. Не увеличивать лимит и не сокращать функции молча.** Размер нельзя оценивать только по сумме распакованных движков или по дополнительному ZIP-архиву, в который GitHub Actions упаковал артефакт.
- Создание установщика автоматически выполняется после успешного билда и обязательных проверок как часть локального пайплайна. Сценарий сборки, описание установщика, настройки зависимостей и workflow GitHub Actions хранятся в репозитории. GitHub Actions вызывает тот же сценарий, что используется локально.
- Обработка файлов локальная и доступна без интернета. Поставка может содержать несколько EXE и DLL: самостоятельность не означает обязательный единственный EXE.

**Пользовательский сценарий.** Правый клик по выделению → Context Actions → готовый пресет либо More Actions… → необходимые настройки → выполнение → открыть результат или показать его в папке.

Для типового пресета запуск происходит сразу, с компактным отображением прогресса. Действия, требующие выбора порядка страниц, шаблона имени или целевого размера, открывают соответствующую форму с разумными значениями по умолчанию. Терминал и технические команды не являются частью пользовательского сценария.

Пример содержимого Context Actions для видео; названия рабочих пресетов уточняются при проверке UX:

| Порядок | Действие |
| --- | --- |
| 1 | Сжать видео — баланс качества и размера |
| 2 | Конвертировать в MP4 / H.264 |
| 3 | Сделать компактную копию / H.265 |
| 4 | Подготовить анимацию для Telegram… |
| Последний | More Actions… / Другие действия… |

Для изображений, документов и таблиц список меняется. При смешанном выделении быстрые команды применимы ко всему выбранному набору; общие действия, например переименование, остаются доступны. В More Actions виден весь каталог, а для выделения отмечены доступные операции и понятные причины недоступности остальных. Дополнительное Office-действие для подходящего типа файла сохраняется видимым и после обнаружения отсутствия Office. Неподдерживаемые файлы не пропускаются без объяснения.

Главное окно сохраняет контекст выделения: список файлов, действие, простые параметры и папка результата. Дополнительные параметры раскрываются по необходимости. Пакетная операция показывает общий прогресс и статус каждого файла. Ошибка одного задания не должна закрывать приложение или мешать увидеть успешные результаты.

Ощущение штатной функции Windows проверяется через системные шрифты и диалоги, светлую и тёмную темы, высокий контраст, масштаб 100–200%, работу клавиатурой и доступность для экранного диктора. Иконка различима при размере 16–32 px и на обеих темах. Название продукта сохраняется как Context Actions, подписи действий локализуются. Язык по умолчанию следует системе, с ручным переключением и английским резервным переводом.

**Повседневные действия — полный целевой объём.**

| Направление | Что должен делать пользователь | Что проверить перед заявлением поддержки |
| --- | --- | --- |
| Видео | Конвертировать распространённые форматы; использовать H.264 для совместимости и H.265 для компактной копии; выбирать качество, разрешение, частоту кадров, звук и целевой размер; выполнять операции пачкой | Матрица входных контейнеров/кодеков и выходных сочетаний; MP4/MKV/MOV/AVI/WebM как начальный набор; корректное воспроизведение, длительность, звук, ориентация и размер; работоспособный программный encoder при отсутствии подходящего GPU |
| Изображения | Конвертировать распространённые форматы, менять размер и качество, выполнять действие для нескольких файлов | JPEG/PNG/WebP/BMP/TIFF/GIF как начальный набор для проверки; направления чтения/записи отдельно; прозрачность, ориентация, цвет и метаданные; сохранение анимации либо явный выбор статичного кадра; HEIF/AVIF и другие форматы расширяют матрицу после проверки комплектных кодеков |
| Документы и PDF | Автономно конвертировать поддерживаемые документы в PDF с явно заданными возможностями; объединять PDF; создавать PDF из изображений и смешанного поддерживаемого набора; дополнительно получать PDF с полным оформлением через Word, если автономный движок его не обеспечивает | DOCX/DOC/ODT/RTF/TXT как кандидаты начальной матрицы; текст, шрифты, изображения и вёрстка; порядок и размер страниц, поля и поворот; защищённые и повреждённые файлы; отдельная проверка дополнительного экспорта с Office и без него |
| Несколько файлов | Переименовывать по шаблону, добавлять префикс/суффикс, заменять фрагмент, нумеровать; выполнять пакетные конвертации | Предпросмотр старых и новых имён, начальный номер и порядок, конфликты, расширения, кириллица и спецсимволы; отмена/восстановление переименования, если исходные условия позволяют; один набор файлов передаётся как одно задание |
| Таблицы | Автономно конвертировать между XLSX/XLS/ODS/CSV и предоставлять поддерживаемый экспорт в PDF; дополнительно экспортировать PDF с полным оформлением через Excel, если автономный движок его не обеспечивает | Чтение и запись каждого целевого формата; листы, типы данных, даты, числа, формулы и оформление; разделитель и кодировка CSV, явный выбор листов; область печати, ориентация и масштаб PDF; отдельная доступность дополнительного экспорта |

«Любой формат в любой» — направление расширения охвата внутри соответствующей категории. Проверяемое обязательство каждой версии задаётся матрицей вход → выход, включая ограничения. Чтение формата само по себе не доказывает возможность записи. Формулы, листы и оформление нельзя терять незаметно; при экспорте в CSV интерфейс объясняет, какие данные сохраняются.

Для размера видео предусмотреть два самостоятельных режима: заданное качество и ограничение размера файла. Второй требует расчёта параметров и проверки фактического результата; одного пресета CRF недостаточно для обещания точного веса. Подстройка может затрагивать битрейт, разрешение и FPS с заранее обозначенными пределами качества.

Для Telegram нужен отдельный пресет анимации. Начальный кандидат — MP4/H.264 без звука с подбором разрешения, FPS и размера; документация Telegram описывает анимации как GIF либо H.264/MPEG-4 AVC без звука. H.265 остаётся отдельным пресетом. Отображение результата как анимации требует практической проверки в целевых клиентах; описание Bot API не заменяет такую проверку. [Telegram: Animation](https://core.telegram.org/bots/api#animation).

Преобразования создают новые файлы и сохраняют исходники. Совпадения имён обрабатываются явно. Для PDF порядок страниц показывается до объединения, поскольку порядок перечисления выделения Проводником не следует считать пользовательским намерением. Успех отображается после проверки результата; отмена или сбой не должны оставлять частичный файл под видом готового.

**Рабочий выбор технологии.** Основной кандидат — **C++20 + Win32 / Windows SDK** для небольшого нативного приложения, CLI и интеграции с Проводником. Сборка — MSVC и CMake. Стандартные элементы Windows предпочтительны; собственный UI framework не создаём. В исходниках 7-Zip есть C, C++ и ассемблер, а Windows-интерфейс реализован на C++ с Windows API; это полезный архитектурный ориентир, но скорость нашего приложения должна подтверждаться измерениями. [Исходники 7-Zip](https://github.com/ip7z/7zip), [код File Manager](https://github.com/ip7z/7zip/blob/main/CPP/7zip/UI/FileManager/FM.cpp).

PowerShell/CMD допустимы как небольшие вспомогательные средства Windows для разработки, сборки и обслуживающих операций, когда это проще. Основной пользовательский путь реализуется нативно. Готовые алгоритмы конвертации берём из комплектных движков; портировать их на C++ не требуется. Текущие скрипты служат исходным материалом для пресетов и сценариев, но не ограничивают итоговую архитектуру.

| Часть | Предложение | Статус выбора |
| --- | --- | --- |
| Интеграция с Проводником | Маленький native COM-компонент с IExplorerCommand; одна модель действий для обоих меню | Документированный путь; проверить регистрацию и реальное поведение на целевых сборках Windows |
| Приложение и CLI | Нативный C++20 / Win32, общий исполнитель действий, запуск обработки вне shell-компонента | Базовый кандидат; подтвердить современный вид, доступность и время старта на прототипе |
| Видео | FFmpeg и ffprobe из каталога приложения, комплектная сборка с нужными декодерами и программными H.264/H.265 encoder | Проверить состав, размер, условия распространения и аппаратное ускорение; не полагаться на PATH. [Документация FFmpeg](https://ffmpeg.org/general.html) |
| Изображения | Системный Windows Imaging Component для штатных форматов; недостающие кодеки поставлять внутри приложения | WIC не гарантирует любой формат и одинаковое наличие дополнительных кодеков на всех ПК. [Документация WIC](https://learn.microsoft.com/en-us/windows/win32/wic/-wic-about-windows-imaging-codec) |
| PDF | Компактные нативные библиотеки для создания PDF из изображений и операций со страницами; qpdf — кандидат для объединения | Генерация и объединение проверяются отдельно; qpdf не заменяет офисный рендерер. [Операции qpdf со страницами](https://qpdf.readthedocs.io/en/stable/cli.html#page-selection) |
| Офисные документы и таблицы | Бесплатные встраиваемые нативные компоненты, проходящие матрицу форматов и бюджет полного сжатого установщика | **Движок не выбран.** Это обязательная проверка реализуемости на первом этапе |
| Сборка и установщик | Общий локальный сценарий MSVC/CMake → проверки → комплектование → упаковка; первый кандидат — Inno Setup / ISCC; GitHub Actions запускает тот же сценарий | Выбрать упаковщик на прототипе; проверить сжатый размер, установку/обновление/удаление и регистрацию обоих меню |
| Настройки и задания | Небольшие локальные настройки и файлы заданий, включая состояние дополнительных Office-функций; постоянный сервис и отдельный сервер БД не требуются | Добавлять инфраструктуру только при конкретной необходимости |

В современном меню Windows 11 обычной записи `shell\command`, запускающей CLI, недостаточно: Microsoft описывает **IExplorerCommand + идентичность приложения**, например через пакет или sparse package. Shell-компонент предоставляет названия, иконки, состояния и дочерние команды, затем передаёт выделение исполнителю. Сканирование содержимого, загрузка движков и конвертация происходят после выбора действия, вне пути построения меню. Классическое меню получает отдельную необходимую регистрацию с тем же набором действий. [Microsoft: интеграция с File Explorer](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer).

```mermaid
flowchart LR
    E[Выделение в Проводнике] --> S[Context Actions: shell-компонент]
    S -->|Быстрый пресет| C[Нативный исполнитель / CLI]
    S -->|More Actions| U[Минимальное окно с выбранными файлами]
    U --> C
    C --> B[Комплектный движок нужной операции]
    B --> R[Проверенный результат и статус]
```

Модель «действие запускает CLI приложения» сохраняется. Для множества файлов потребуется корректная передача полного списка, например через локальный файл задания, чтобы не упираться в длину командной строки. Пути передаются как данные, без подстановки в исполняемый текст CMD/PowerShell. Для пользователя это один запуск на одно выделение, без всплывающего терминала.

Поставка — один установщик с локальными файлами приложения и движков. Начальный вариант для проверки: нативный установщик и sparse package для идентичности; окончательный способ выбирается после проверки обоих меню, установки обычным пользователем, обновления и удаления. Self Packaged само по себе не означает MSIX и не отменяет регистрацию расширения в ОС. Расположение верхнего пункта контролирует Windows; Microsoft также анонсировала для Insider новые настройки размещения расширений. Нужно проверить актуальные поддерживаемые сборки и пользовательские настройки, сохраняя требование доступности Context Actions в обоих меню. [Microsoft: изменения меню, август 2026](https://blogs.windows.com/windows-insider/2026/08/17/improving-file-explorer-context-menu-faster-simpler-and-more-customizable/).

**Выбор установщика и пайплайн сборки.** Отдельная задача первого этапа — выбрать средство, которое автоматически создаёт полный установщик без ручной работы в GUI. Первый кандидат — **Inno Setup с ISCC**: он поддерживает сборку из командной строки и сжатие LZMA/LZMA2. Сравнить его с упаковкой средствами Windows SDK/MSIX по фактическому размеру, времени установки, регистрации расширения, обновлению, удалению и локализациям. При использовании CPack рассмотреть готовый Inno Setup generator; выбрать один источник описания состава поставки, без параллельных расходящихся рецептов. [ISCC](https://jrsoftware.org/ishelp/topic_compilercmdline.htm), [сжатие Inno Setup](https://jrsoftware.org/ishelp/topic_setup_compression.htm), [CPack Inno Setup](https://cmake.org/cmake/help/latest/cpack_gen/innosetup.html).

Подбор сжатия оценивается по полному установщику: итоговый размер, время упаковки, время установки и потребление памяти при распаковке. Не обещать коэффициент сжатия по сумме размеров DLL. Установщик должен содержать все обязательные компоненты, а необходимые для сборки инструменты не должны превращаться в зависимости на машине пользователя. При выборе конкретной версии упаковщика сохраняется требование бесплатных компонентов; учитывать её условия использования. [Лицензия Inno Setup](https://jrsoftware.org/files/is/license.txt).

| Файл / каталог | Назначение |

| `.github/workflows/build-windows.yml` | Сборка на Windows runner в GitHub Actions, вызов общего сценария и сохранение результатов как workflow artifacts |
| `docs/build.md` | Команда локальной сборки, необходимые инструменты, структура результата и способ повторить ошибку CI локально |

Версии toolchain, упаковщика, движков и их зависимостей фиксируются в конфигурации репозитория; внешние бинарные входы проверяются по контрольным суммам. Локальная и CI-сборка используют одинаковые конфигурации и состав поставки. Кэш ускоряет получение зависимостей, но чистая сборка без кэша тоже должна работать. Скачивание входов на этапе разработки/сборки не меняет требование полностью автономной установки и работы готового приложения.

Последовательность общего сценария:

1. Подготовить зафиксированные инструменты и зависимости, сконфигурировать проект и собрать Release для выбранной архитектуры.
2. Выполнить обязательные проверки; при ошибке завершить сценарий с ненулевым кодом, не выдавая старый установщик за новый результат.
3. Собрать отдельный каталог поставки из результатов текущего билда: приложение, shell-компонент, движки, DLL, локализации, manifests и необходимые сопроводительные файлы.
4. Автоматически вызвать выбранный упаковщик и получить полный установщик. Версию и архитектуру брать из конфигурации сборки. Если предусмотрена подпись, итоговый размер проверять после неё.
5. Измерить сам установщик: до 100 МБ — целевой результат; от 100 до 300 МБ включительно — допустимый; выше 300 МБ — проверка не пройдена, требуется обсуждение нового лимита с пользователем. CI сохраняет отчёт о превышении, не повышает лимит автоматически.
6. Проверить установку, запуск комплектного CLI и удаление на чистой Windows в изолированной тестовой среде. Визуальную проверку обоих меню и UI выполнять отдельно: успешный консольный прогон на runner её не заменяет.
7. Сохранить установщик, SHA-256, отчёт о сжатом/установленном размере и результаты проверок в выходном каталоге. GitHub Actions сохраняет их как артефакты сборки. [Артефакты GitHub Actions](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).

Планируемые запуски workflow: изменения проекта в push/pull request и ручной запуск. YAML занимается подготовкой Windows runner, вызовом общего сценария и сохранением результатов; логика сборки и упаковки остаётся в репозитории и запускается локально без GitHub. Создание установщика и сохранение CI-артефакта не означают автоматический публичный релиз. Этот раздел задаёт требования к будущей реализации; сам пайплайн в текущей заметке ещё не создан.

**Нерешённый технический вопрос: документы и таблицы.** Пока не подтверждено, что бесплатный компактный набор закрывает все необходимые автономные направления и базовый экспорт в PDF при размере полного сжатого установщика не более 300 МБ. Для PDF с полным оформлением согласован дополнительный путь через Office, если такой результат недоступен автономно. Небольшая библиотека чтения таблиц не равна полноценному офисному конвертеру: например, XLSX I/O ориентируется на значения и не сохраняет формулы/вёрстку, а libxls читает XLS. Эти проекты иллюстрируют ограничения, а не являются выбранным окончательным решением. [XLSX I/O](https://github.com/brechtsanders/xlsxio), [libxls](https://github.com/libxls/libxls).

Полный LibreOffice не принимается базовой зависимостью автоматически: сохраняются требования к лёгкому стеку и отзывчивости. Более крупный комплектный движок оценивать по реальным зависимостям, поведению и размеру полного сжатого установщика. Большой установленный объём сам по себе не означает превышения бюджета. Если установщик превышает 300 МБ, обсуждать новый лимит с пользователем. Поддержку документов и таблиц сохранять в целевом объёме; урезанный экспорт только значений не выдавать за выполненную конвертацию. Собственный универсальный офисный движок не начинать без отдельного обоснования масштаба.

**Проверенные варианты Microsoft.** Рассмотреть системные API и готовые средства Microsoft при выборе стека. Наличие Windows не означает наличие Excel или Word. По документации найдены следующие возможности; практических конвертаций этими средствами в рамках подготовки заметки не выполнялось.

| Вариант | Что даёт | Соответствие самостоятельной поставке |
| --- | --- | --- |
| Open XML SDK | Работа со структурой документов OOXML, включая XLSX/DOCX | Может обрабатывать формат без автоматизации Office, но это .NET SDK, а не встроенный конвертер Windows. Не закрывает старый бинарный XLS, ODS, офисную вёрстку, пересчёт формул и экспорт в PDF. [Назначение SDK](https://learn.microsoft.com/en-us/office/open-xml/about-the-open-xml-sdk), [официальные ограничения](https://learn.microsoft.com/en-us/office/open-xml/open-xml-sdk-design-considerations) |
| Windows Packaging API / MSXML | Нативное чтение и изменение частей OOXML-пакета | Полезно для отдельных операций из C++, но само по себе не даёт модель Excel/Word и рендеринг документов. | Windows.Data.Pdf | Загрузка существующего PDF и доступ к его страницам | Системный API полезен для просмотра; он не является конвертером XLS/DOC в PDF. [PdfDocument](https://learn.microsoft.com/en-us/uwp/api/windows.data.pdf.pdfdocument?view=winrt-26100) |

**Принятое решение по Office.** Обязательные функции автономны. Если нельзя получить PDF с полным исходным оформлением без Office, соответствующее действие становится дополнительным и использует установленный Excel или Word. Установленный Office не считается комплектным движком и не подменяет обязательный автономный набор. В размер установщика входит наш компонент интеграции, но сам Office не поставляется с Context Actions.

Дополнительная функция присутствует в софте и при отсутствии Office. Для подходящих файлов она видна в каталоге действий и в тех местах контекстного меню, где предусмотрена. До первой попытки её состояние неизвестно, и пользователь может её выбрать. При первой попытке проверяется нужная возможность: Excel для таблиц, Word для текстовых документов. Результат записывается в небольшой локальный файл, например `%LOCALAPPDATA%\Context Actions\capabilities.ini`; конкретное имя файла — предложение реализации. Проверка не выполняется при каждом открытии меню или запуске приложения.

| Состояние | Поведение |
| --- | --- |
| Ещё не проверено | Действие доступно для первой попытки; проверка запускается только после его выбора |
| Доступно | Действие выполняется через соответствующее приложение Office; сохранённое состояние используется без отдельной повторной проверки наличия |
| Недоступно | При обнаружении показывается понятное сообщение, например «Для сохранения исходного оформления требуется Microsoft Excel». Действие остаётся видимым с отметкой недоступности и причиной; состояние сохраняется между запусками |

В More Actions предусмотреть явное **«Проверить снова»**, чтобы после установки или восстановления Office обновить сохранённое состояние. Это осознанное повторное действие пользователя, а не фоновый опрос. Если ранее доступный Office удалён или перестал запускаться, ошибка фактического выполнения обновляет состояние и объясняется пользователю. Проверки Word и Excel независимы: наличие одного не означает наличие другого. При временной ошибке файла не помечать всё приложение Office отсутствующим.

Автономный экспорт и дополнительный экспорт с полным оформлением различаются в интерфейсе по результату и условиям доступности. Не переключаться незаметно с сохранения оформления на упрощённый PDF. Качество результата через Office также проверяется на реальных документах: использование COM само по себе не является доказательством идеального результата. Ни один из проверенных вариантов Microsoft сам по себе не подтверждает весь обязательный автономный объём XLS/XLSX/ODS/CSV и PDF в пределах бюджета установщика.

**Этапы дальнейшей разработки.** Порядок отражает зависимости, а не оценку сроков. Каждый этап завершается проверяемым результатом.

После каждого изменения состава движков или параметров сжатия автоматически пересобирать и измерять установщик. Отчёт содержит два самостоятельных показателя: размер готового сжатого установщика, по которому проверяется лимит 100/300 МБ, и установленный объём для информации. Ведомость компонентов содержит версии/конфигурации, архитектуру, транзитивные зависимости и распакованные размеры уникальных файлов, включая языки, шрифты и runtime. Вклад компонента в размер сжатого установщика можно оценивать сравнением пробных сборок; при совместном сжатии эти вклады не следует просто суммировать. **В этой заметке нет измеренного размера установщика:** окончательный набор движков и рецепт упаковки ещё не выбраны.

Языковые ресурсы, доступность, сохранность файлов и возможность корректной отмены закладываются с первых этапов. Финальный этап завершает их проверку, а не добавляет эти требования впервые. Начальная целевая архитектура по рабочему допущению — Windows 11 x64; ARM64 требует отдельной комплектной сборки и проверки shell-компонента.

**Критерии быстродействия и готовности.** Предлагаемые ориентиры для прототипа: вклад нашего компонента в построение меню — p95 до 50 мс; готовое к вводу окно More Actions — до 1 секунды при холодном старте и до 0,5 секунды при повторном запуске на зафиксированном тестовом ПК. Это проектные цели, не текущие результаты. Замеры выполнять на одинаковом наборе файлов с описанием оборудования и состояния запуска. Стоимость чтения метаданных и запуска конвертера измерять отдельно. Пока нет задания, движки не работают; задержка офисного движка не должна блокировать появление окна.

Готовность продукта означает: обязательные автономные действия всех пяти категорий проходят полный путь от выделения до проверенного результата; оба меню работают; имя и иконка читаемы; More Actions сохраняет выделение; все пять локализаций проверены; исходники защищены; полный сжатый установщик соответствует бюджету; зависимости комплектны; пайплайн из репозитория автоматически собирает установщик локально и в GitHub Actions. Проверка на чистой машине включает отсутствие отдельно установленных FFmpeg/Office/Python, отключённую сеть, пути с кириллицей/пробелами/спецсимволами, длинные пути, конфликты имён, повреждённый файл, отмену и пакет со смешанными результатами. Для дополнительного экспорта через Office проверяются отсутствие, наличие только Word, наличие только Excel, наличие обоих, сохранение состояния после перезапуска, ручная перепроверка после установки и корректная ошибка после удаления Office.

Для публичной поставки на этапе выбора компонентов проверить условия распространения конкретных сборок и включить необходимые notices и материалы. Бесплатность компонента не определяет автоматически состав этих обязательств. [Условия FFmpeg](https://ffmpeg.org/legal.html). Не выбирать зависимости только по размеру одной DLL, не учитывая сопровождающие файлы.

**Текущая отправная точка.** В рабочем каталоге на момент подготовки находятся `convert-video.cmd`, `video-compress-ui.ps1`, `install-context-menu.cmd`, `uninstall-context-menu.cmd`. По чтению исходников это прототип HEVC-конвертации с профилями качества, небольшими WinForms-диалогами через PowerShell и регистрацией команды для видео через реестр. FFmpeg/ffprobe берутся из PATH. Это материал для первого сценария, а не доказательство готовности Context Actions; выполнение и установка этих скриптов при подготовке плана не проверялись.

Референс просмотрен из ранее созданного локального файла: `macos-finder-daily-drive-showcase-ru.pdf`. Все шесть страниц проверены: видео, изображения, PDF, пакетное переименование и соседние функции Finder. Отдельное новое вложение в доступных материалах не обнаружено. Из референса берём короткий путь к действию, контекстность и разумные настройки; дополнительные функции последнего слайда не добавляют автоматически новые обязательства к этому плану.
